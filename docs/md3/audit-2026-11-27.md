## 2. Monet 取色审计：**不符合规范**

现状（`MainActivity.kt` 约 2380-2430 行）：

```kotlin
// 1. 用 androidx.palette 从「软件壁纸」位图上直接取一个 vibrant 颜色当种子
val c = pal.getVibrantColor(0) ... ?: pal.getDominantColor(0)
// 2. 然后手工 lerp M3 默认 scheme 的若干槽位
Palette.m3 = base.copy(
    primary = seed,                                   // ← 种子直接当 primary
    surfaceContainer = lerp(base.surfaceContainer, seed, 0.16f/0.08f),
    secondaryContainer = lerp(base.secondaryContainer, seed, 0.45f/0.22f),
    ...
)
```

与规范冲突的点：

1. **没有色调板（tonal palette）**。M3 的角色色来自「种子 → HCT 色调板 → 各角色取固定色调值（如 primary 浅色 tone 40 / 深色 tone 80）」。我们直接把 wallpaper 取到的任意色调色当 `primary`，角色之间的亮度关系（primary/onPrimary 对比、container 与 onContainer 配对）无法保证。
2. **`onPrimary` 等配对角色没跟着算**，仍是默认值（近似白/黑），遇到浅色种子就是「白字压浅底」，正是规范里列出的常见错误 3。
3. **`androidx.palette` 不是 Material Color Utilities**。Palette 的 Vibrant/Dominant 是「图片主色」，与 MCU 的 Celebi 量化 + Score 打分不是同一套算法，产出的种子不可复现也不保证可访问性。
4. **深色方案不是独立色调选择**：代码用 `lerp` 往深色里掺色，属于手工调，不是按深色 tone 重新取。
5. `surfaceContainer`/`secondaryContainer` 用 alpha 比例的 lerp 当背景，也踩了规范「不要用 copy(alpha) 叠加当背景，应该用对应 container 角色」。

结论：**当前 Monet 是「视觉上像动态取色」，不满足 M3 动态配色规范**（对比度与角色配对无法保证）。

### 修复路径（二选一）

- **A. 引入 Material Color Utilities**：`QuantizerCelebi + Score` 取种子 → `Hct.fromInt(seed)` → `SchemeTonalSpot`/`SchemeContent` 生成完整 scheme（primary/onPrimary/container/surface 全套）→ 映射进 `ColorScheme`。这是真正符合规范的做法，但需要新增依赖（当前机器上 `com.google.android.material:material` 的仓库里只有旧版本，需确认可用版本或直接引 MCU 的 java 库）。
- **B. 不做自定义莫奈**：API 31+ 直接用系统 `dynamicLight/DarkColorScheme(context)`（系统已按 HCT 生成），API < 31 用 Material Theme Builder 导出的固定 scheme。缺点：与「软件壁纸」不一致（系统用的是系统壁纸）。

> 现状介于两者之间：既不是系统 dynamic，也不是 MCU 生成，属于手工配色。
